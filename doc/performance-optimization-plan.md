# 搜索与页面加载优化实施记录

## 目标与边界

在保持搜索语义、多用户隔离、联系人名称优先级及用户数据完整的前提下，降低首次加载、正文搜索和并发请求的等待。1～2 秒 p95 是待实测的目标，不是未经验证的性能承诺。生产镜像仅在本机 Docker 构建，涉及 schema 按 L2 备份，不压缩整份邮件目录。

## 实施清单

- [x] 分阶段耗时：索引候选、精确统计、列表、会话摘要和连接池等待；不输出搜索词或邮件内容。
- [x] 候选复核执行计划优化，保留 LIKE 和用户/状态复核，不截断结果。
- [x] 列表先返回，独立接口返回精确总数；兼容旧接口调用，界面明确统计中/失败。
- [x] 用户隔离、有界短缓存及同请求合并，写入提交后失效，取消不影响其他等待者。
- [x] 会话最新邮件改为批量摘要，移除列表读取正文和逐条查询。
- [x] 统一邮件排序时间和组合索引，幂等兼容迁移，历史数据分批补齐。
- [x] 前端内存列表缓存、后台刷新、请求取消与旧响应保护。
- [x] 联系人按当前页地址解析，保留昵称/名称和唯一账号前缀匹配，通讯录与写信仍可检索。
- [x] SQLite/MySQL 一致性、迁移、缓存失效、取消、用户隔离与前端回归。
- [x] 本机镜像构建、NAS L2 备份/部署/回滚方案、首轮与预热和并发验收（未主动清空共享数据库缓存）。

## 验收要求

固定样本核对搜索总数、分页顺序、收/发件箱、日期、账号、文件夹、已读/星标/垃圾/删除状态。缓存不得跨用户；新增、解析修复、状态改变及账号/联系人更新不得依赖长 TTL 才可见。客户端取消共享请求时不得取消其他用户或等待者的工作。精确总数未返回时不展示假的 0 或最后一页。

性能测量需区分接口阶段耗时与浏览器端到端耗时，区分首次、重复和三个并发请求；不主动清空共享 MySQL 缓存，不贸然修改共享数据库全局参数。

## 查询与缓存设计

- 摘要列表支持 `includeTotal=false`；`total=null` 表示尚未统计，不是 0。列表多取一条判断 `hasMore`，没有精确总数时仍可翻页。
- `GET /api/v1/messages/count`、`GET /api/v1/threads/count` 接受与列表相同的过滤条件，返回精确 `total` 和数据 `revision`；接口均鉴权并使用统一 envelope。旧列表调用不传新参数时仍返回精确总数。
- 新前端计数使用 `deferred=true`：服务端最多等待 150ms，未完成返回 HTTP 202，envelope 的 `httpCode=202`、`success=true`、`data.total=null`、`data.totalPending=true`。前端每秒以可取消的短请求轮询，完成返回 HTTP 200 和精确总数；不延长 Axios 的 15 秒超时。后端统计仍有 30 秒工作上限，前端轮询整体最多 90 秒，失败常驻并允许重试。
- 版本不是跨请求数据库快照。前端以请求代次拒绝旧响应，仅在列表和统计版本一致时缓存带总数的页面；正常收取新信期间总数可能随后改变。
- 后端缓存 3 秒、最多 128 项/64 个不同在途工作，键包括用户、完整查询参数、搜索模式及提交版本；候选数据也合并相同查询。写入提交推进版本，回滚不推进；索引 outbox 确认不影响业务缓存。
- 普通摘要请求最后一个等待者离开会取消；异步计数 flight 则跨短轮询持有工作，原有工作上限仍为 30 秒。轮询租约为 5 秒，切换关键词或离开页面后不再轮询，过期即取消遗留工作，避免快速搜索堆积旧计数。失败任务状态保留 3 秒供轮询读取，不作为成功业务数据缓存，任务数量同样有界。
- 前端内存缓存 15 秒、最多 24 页，不落盘；以登录会话隔离，修改业务、退出登录或切换会话即清空，并用 epoch 阻止旧请求重新填入缓存。缓存显示后仍后台请求新数据。
- MySQL 的候选检索显式用主键范围访问；列表先读取轻量元数据排序，再以每批 64 条进行原 LIKE 复核，越过当前页 offset 并找齐 pageSize/hasMore 后停止。候选不截断；低命中率或深页仍需更多批次，不保证所有搜索固定耗时。精确计数仍需复核完整命中范围。
- `sort_at=COALESCE(sent_at,received_at,created_at)`，新增可空派生列并分批补齐；保留原始日期，旧代码写入空值后重新升级会修正。新增索引仅派生结构，回滚旧程序时可保留，禁止默认回灌整库覆盖新邮件。
- 慢阶段日志只记录用户 ID、阶段、候选数、连接池区间统计及耗时；连接池等待差值为进程级区间量，不冒充单请求精确等待，不记录搜索词或正文。

## 联系人与前端交互

`POST /api/v1/contacts/resolve` 接收最多 256 个地址键，支持标准“名称 <邮箱>”和账号前缀。后端仅在当前用户的完整通讯录上判定前缀是否唯一，返回精确/唯一匹配及 `ambiguousPrefixes`；前端不能根据局部已加载联系人猜测唯一性。当前页地址过多时分批解析，写信通过原通讯录搜索接口防抖查询 50 条，不改变通讯录管理能力。

邮件、会话、总数和联系人均有请求取消与旧响应保护；切换筛选不允许旧计数覆盖新结果。未完成统计时保留上下页图标，失败说明和重试入口持续可见，不以短暂 toast 作为唯一反馈。

## 已完成的本机验证

- `go test ./...`；存储/接口/检索引擎 `go test -race`。
- 独立 Docker MySQL 测试库：新旧搜索一致、取消、排序兼容迁移、联系人歧义与隔离、跨 64 条边界的低命中率及深页不漏信。
- 前端 `npm run build`，页面改为懒加载；仍存在共享 UI 库大 chunk 警告，没有掩盖或盲目升级依赖。
- 本机浏览器模拟：列表约 175ms 出现而统计仍在等待；统计故障常驻、重试成功；昵称按需解析，首屏无全量联系人下载；390px 窄屏无整页横向溢出。模拟数据不作为生产速度承诺。
- 浏览器慢旧计数/快速新搜索验证：旧列表与旧总数均不覆盖新结果，防抖后新关键词仅请求一次；内存缓存跨用户隔离、返回副本及写入 epoch 防旧响应回填通过。
- 新增真实后端 202/200 envelope 测试、异步工作跨轮询存活/合并/失败状态回归；浏览器模拟验证 202 等待、后续得到精确总数以及失败重试，不能把 `total=null` 当成 0。

## 生产验收（2026-10-17）

前后端镜像版本为 `20261017-read-perf-r5`，均由本机 Docker 构建。沿用生产 MySQL、Bleve active 配置和原数据挂载；升级前执行 L2 一致性数据库备份并校验 gzip，约 25MB，未压缩整份邮件目录。保留旧镜像及配置用于程序回退，不默认恢复整库覆盖升级期间的新邮件。
