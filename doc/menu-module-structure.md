# 菜单模块目录规范

## 目的与适用范围

前后端以菜单业务树作为代码导航结构：看到菜单，就能找到对应目录；看到目录，就能判断业务归属。菜单专属代码集中维护，公共能力独立复用，避免页面、handler 和请求长期堆在扁平目录或大文件中。

本规范是新增开发与后续重构的强制目标，不代表现有代码已完成搬迁。本次只调整文档，不改变路由、数据库或运行行为。

## 菜单与业务键

| 菜单或入口 | 统一业务目录 | 说明 |
| --- | --- | --- |
| 邮件 | mail | 列表、详情、写信、回复、转发、导入等子功能 |
| 附件中心 | attachments | 附件检索、预览与下载入口 |
| 邮箱账号 | accounts | 账号维护、授权、连接测试及同步状态 |
| 联系人 | contacts | 通讯录维护与联系人查看 |
| 规则 | rules | 规则维护、预览、应用及命中记录 |
| 发送记录 | sendlogs | 使用合法 Go 包名；现有 URL /send-logs 不变 |
| 设置 / 个人资料 | settings/profile | 包含资料、头像与修改密码界面 |
| 系统管理 / 用户管理 | admin/users | 用户管理页面及对应管理接口 |
| 系统管理 / 系统版本 | admin/version | 管理页内子功能，目前不是独立菜单或路由 |
| 登录、注册、OAuth 回调 | auth | 非菜单入口，作为独立认证模块组织 |

使用稳定英文业务键；中文菜单改名、排序、折叠不要求同步修改目录。新增真实业务子菜单时按父子关系增加目录，并更新本表。收件箱、发件箱、草稿等视图与筛选属于 mail，不为每个按钮、标签页或状态创建空模块。

## 前端目标结构

下列为目标示例，不是当前文件清单；只创建实际有内容的目录与文件。

~~~text
mailnest-fe/src/
  modules/
    mail/
      pages/                  # 邮件页面
      components/             # 邮件专属组件
      composables/            # 邮件专属组合逻辑
      compose/                # 写信子功能，包含其组件和逻辑
      api.ts
      types.ts
    attachments/
    accounts/
    contacts/
    rules/
    sendlogs/
    settings/
      profile/
    admin/
      users/
      version/
    auth/
  components/                 # 跨模块组件、布局
  api/client.ts               # 请求客户端与 envelope 解包
  stores/                     # 真正共享的会话、应用状态
  utils/                      # 无菜单归属的通用工具
  router/                     # 路由装配、懒加载与守卫
~~~

- 业务专属组件、状态、请求和类型跟随模块；只有跨模块复用的内容才进入公共目录，不将整个业务页面放进公共 components。
- 沿用现有公共目录，不再平行建立另一套 shared 请求客户端或鉴权状态。模块专属状态放模块内部，不继续堆入全局 stores。
- router 统一装配页面并保留懒加载、鉴权和原 URL；各模块不自行建立相互竞争的路由实例。
- 跨模块只引用明确公开的接口、类型或组件，禁止通过相对路径深入其他模块私有实现。仅被一个菜单使用的代码默认留在该菜单内。

## 后端目标结构

~~~text
mailnest-be/internal/
  api/                        # HTTP 路由、中间件与依赖装配
  modules/
    mail/
      handler.go              # 该模块 HTTP 入口与 DTO
      service.go              # 该模块用例，按实际复杂度拆分
      repository.go           # 按需定义最小存储接口
      compose/                # 有明确边界时再拆子包
    attachments/
    accounts/
    contacts/
    rules/
    sendlogs/
    settings/
      profile/
    admin/
      users/
      version/
    auth/
  storage/                    # 数据库连接、集中迁移及现有存储实现
  mail/                       # 现有跨菜单邮件领域与协议能力，渐进整理
  searchindex/                # 共享派生索引能力
  buildinfo/                  # 共享构建版本信息
~~~

认证、配置、加密、统一响应等现有公共包保留独立职责，位置以实际仓库为准；上图省略它们，不表示删除或合并。

- 菜单模块承接对应业务入口和用例，内部按职责拆文件，不强制每个简单模块都创建一套空 handler/service/repository。
- 由装配层注入数据库、业务服务、日志等依赖。模块不得导入 api.App，也不得导入其他模块的 handler；父目录仅作分组，不建立被子包反向引用的聚合包。
- 依赖方向为“装配层 → 模块入口 → 业务服务 / 存储接口 → 基础设施实现”，基础设施不反向依赖 HTTP 菜单层。存储接口由使用方按需定义，装配时连接实现。
- 多菜单共同使用的邮件解析、联系人名称解析、附件授权、SMTP/IMAP、索引、后台任务等通过公共领域服务或接口复用，不为了目录对称复制业务代码。
- 个人资料界面的修改密码可调用统一认证服务；邮箱 OAuth 配置调用共享授权能力。页面归属不等于复制认证、凭据或存储机制。
- GORM 模型、表结构迁移与数据库连接统一管理，不为每个菜单建立独立数据库，不因搬文件重命名生产表或修改数据目录。
- 跨模块查询仍必须携带当前用户上下文，复用统一 envelope 和鉴权；目录隔离不能替代数据权限隔离。

## 文件拆分与公共边界

- 单文件建议控制在约 300～500 行；超过时评估是否混入多个职责，按业务子功能拆分，不以凑行数机械切文件。
- 共享代码必须有明确职责和真实复用需求，不把未分类业务塞入 helpers、common 或 utils。
- 前后端共享的是业务命名和菜单层级，不要求每个技术文件一一对应；定时任务、协议、存储、命令行工具无需伪装成菜单模块。
- 测试跟随所属模块；迁移公共实现时保留其独立回归测试，业务测试不能只依赖目录或文件存在。

## 渐进迁移与验收

1. 从联系人或设置 / 个人资料等边界清晰的模块开始，记录旧文件、新目录、公共依赖和未迁移部分，再处理大型邮件模块；本规范不代表已经启动整库迁移。
2. 每批只迁移一个可验证范围，先整理依赖和测试，再移动代码、更新 import、路由懒加载与构建配置。迁移期可保留薄转调入口，不保留两份业务逻辑。
3. 新功能直接采用目标目录。修改旧模块时，至少将新增的独立子功能按规范归属；如暂时受循环依赖或旧结构限制，必须在变更记录说明兼容入口、原因及后续迁移事项，不以此永久继续堆积大文件。
4. 保持 API 地址、请求响应、登录态、用户隔离、菜单权限、邮件数据路径和数据库 schema 兼容；纯代码搬迁不触发生产数据迁移。禁止夹带无关依赖升级或数据库清理。
5. 前端运行类型检查及构建并验证相关页面；后端运行受影响模块及公共依赖测试，迁移装配或公共鉴权时补全量回归。重点验证旧路由、权限、列表、详情、附件及对应业务操作。
6. 更新本表、后端包结构说明及 CHANGELOG.md，区分“规范目标”“已迁移”“仍保留”。生产发布另按升级与备份规范执行，不因目录调整跳过安全检查。
