# Bleve 邮件检索设计与切换方案

## 目标与边界

使用 Go 进程内 Bleve 2.6.1（Scorch 磁盘索引）加速主题、发件人、收件人、抄送和已解析正文搜索，不增加独立搜索容器。SQLite、MySQL、PostgreSQL 继续作为正式数据库；原文、正文和附件文件仍按原路径保存。索引是可以重建的派生数据，不能用索引恢复正式数据，也不能因重建索引清空邮件。

当前不抽取附件里的 PDF/Word 文字、不做语义搜索或中文词义分析。中文采用去重单字与连续双字候选，不是直接使用默认英文分词器。保留已有子串查询和日期、账号、文件夹、已读、星标、垃圾箱、回收站等筛选，不改为相关度排序。

## 配置

历史配置默认 search.engine 为 database，不会在升级时突然建立全量索引。首次显式启用示例：

    search:
      engine: bleve
      mode: shadow
      path: ""
      batchSize: 25
      batchDelayMs: 50
      maxCandidates: 20000

- engine：database 或 bleve。database 是安全回退开关。
- mode：shadow 只做候选抽样验证，结果仍由数据库返回；active 用索引候选缩小数据库查询范围。首次建议 shadow，核对后修改配置重启，不会自动切 active。
- path：为空使用 app.dataDir/search，必须持久化到本地磁盘，不放一次性容器层，不允许多个写进程共用，不建议网络文件系统。
- batchSize：默认 25，最大 200，每轮增量任务和历史回填各至多一批。
- batchDelayMs：有工作时默认休息 50 毫秒，空闲约每秒检查，处理失败约 3 秒再检查。小批减少 NAS 内存和 I/O 峰值，但仍须观察实际资源占用。
- maxCandidates：默认 20,000，最大 50,000。候选或待处理邮件过多时回退数据库，绝不静默截断结果。

启用 Bleve 后，不叠加 MySQL FULLTEXT 条件；原显式 MySQL 运维命令作为兼容能力保留，本方案不要求建立 MySQL FULLTEXT。索引打开失败或目录锁冲突时继续数据库搜索，状态入口显示中文说明。

## 检索与用户隔离

文档 ID 为“用户ID/邮件ID”，user 字段精确匹配。五个文本字段只存去重 token，不存正文副本、位置向量或排序值。基本汉字、ASCII 字母（小写）和数字生成单字及双字集合。例如“张海涛”包含张、海、涛、张海、海涛；601 包含 6、0、1、60、01。重复长正文先去重，避免逐位置 token 流膨胀。

查询最多选 8 个必要片段；字段内 AND，全部搜索在五字段间 OR，不把输入当成 Bleve 查询语法。百分号、下划线等 LIKE 通配符断开片段；反斜线或没有安全片段时回退。单字也建索引，不受 MySQL ngram 停用词和英文最短词长限制。

数据库排序规则对重音、全角、组合字母等可能有不同等价关系。字段含非基本汉字/ASCII 的 Unicode 字母、数字、组合字符、不可见格式符时标为不确定，该字段候选保守放行后交 SQL 复核。这类内容多时加速效果会下降。特殊自定义排序规则仍须 shadow 对比，不能假定覆盖所有自定义等价行为。

最终查询继续执行原 LIKE、user_id、账号/文件夹/状态过滤以及排序分页。索引也强制用户条件，并校验结果 ID 前缀，不能返回其他用户的 ID、计数或正文。日期、状态、本地文件夹改变立即由数据库反映，无需等重建。邮件列表和会话列表共用候选能力；草稿、联系人和日志搜索不在此次范围。

## 事务任务与一致性

新增 mail_search_tasks 表只保存事件 ID、用户、邮件 ID、重试次数和下次重试时间，不复制正文或凭据。新邮件插入、解析修复与任务在同一事务提交，任务写失败则邮件事务回滚。重复导入不新增任务。GORM 为旧库增量补表，不改写正式邮件。

单写工作器按事件 ID 小批读取最新邮件，提交 Bleve 后才确认本批精确事件 ID。重放是幂等覆盖；读取后出现的更新拥有新事件 ID，不会被旧批确认。任务不自动丢弃，失败按 1–256 秒指数退避。重建期间需同时写活动和构建中索引，任一失败均保留任务。

查询必须先读当前用户未确认的邮件 ID，再读活动索引，合并后由 SQL 复核。索引延迟或失败重试时，新信和正文更新仍可搜到。顺序不能反过来，否则工作器可能在两次读取间提交索引并删事件，形成漏信竞态。查询开始后才提交的新事务按正常并发语义由下次搜索看到。

当前删除为软删除，由数据库立即过滤。未来物理删除、批量正文改写或直接 SQL 修改搜索字段，必须同事务写任务，或完成后强制重建。不能假定索引会自动知道运维脚本的修改。停用 Bleve 时任务仍保留，重启后可追赶；长期停用会积累任务，可另行设计安全清理，不能直接删队列。

## 历史回填与重建

1. 首次启用或管理员重建时取最大邮件 ID，建立独立 index-v1-时间戳目录，不覆盖旧索引。
2. 按 ID 游标扫描，每批与增量事件交替处理；不一次加载全部正文，不重复读附件/原文。
3. 游标与扫描上界通过 Bleve Batch 内部键和本批文档一起提交，重启按已提交检查点续建，避免游标领先于索引。
4. 扫描结束且增量队列追平后，fsync 临时清单、原子 rename 替换 manifest.json，再切活动指针。构建期间旧索引继续服务；首次构建回退数据库。
5. 正常发布保留当前和上一代，仅清理清单明确记录的更早代际。不遍历删未知目录，损坏或未登记目录保留人工核查。

根目录初建权限 0700，锁文件 0600。索引也是敏感数据，不得提交仓库。writer.lock 是 OS 文件锁，进程退出自动释放，锁文件存在不表示仍被占用。损坏索引保留并重建，期间数据库可用；清单无法解析或版本未知时不覆盖，应改用新的空索引路径。

关闭服务先取消并等待工作器，释放磁盘锁，最后关闭数据库。HTTP 支持 SIGTERM 优雅退出。中文日志不记录搜索词、邮件正文或授权信息。

## 状态与接口

- GET /api/v1/search/status：需要登录，只统计当前用户进度、待处理和重试。管理员额外看到进程内全局 shadow 抽样计数，不提供其他用户明细。
- POST /api/v1/admin/search/rebuild：管理员专用，202 为后台受理；已有重建则 409，不并行建索引。
- 成功和错误均使用统一 envelope，httpCode 与 HTTP 状态一致。
- 邮件页筛选行右侧小图标打开状态，不扩大搜索区。仅面板打开时轮询，忙时约 5 秒、空闲约 30 秒，关闭和离页取消请求，后台标签页减少请求。失败说明保留在面板。
- shadow 比较邮件列表当前页 ID 是否被候选包含，是抽样，不代表全量一致性证明，不自动据此切换。计数重启清零。上线验收还须比较总数和分页 ID。

## 上线与回退

2026-10-17 已完成生产部署，版本 `20261017-bleve-search`，先 shadow 回填并核对，再切换 active。后续首次启用或重新部署仍须按以下步骤执行：

1. 本机 Docker 构建镜像。新增任务表按 deployment-backup-strategy.md 做 L2 配置/数据库备份，不全量压缩几十 GB 邮件。确认持久化挂载、加密密钥、连接和剩余磁盘空间。
2. 保留旧镜像、Compose 和配置，单后端替换。先用 bleve + shadow，验证健康、登录、列表、会话、详情、附件、账号和规则。
3. 观察进度、重试、CPU/内存/I/O；用中文单字、数字、邮箱、主题/正文、日期/账号/文件夹组合核对总数和分页 ID，检查新增、导入、解析修复和删除。
4. 核对后改 active 并重启，实测冷/热及并发查询 p50/p95。宽泛搜索或特殊文本可能回退，不能承诺所有查询毫秒级。
5. 回退优先改 database 并重启，不恢复旧数据库覆盖新信，不删正式数据。previous 已停止接收更新，不能直接指回旧索引当回滚。若退回旧代码版本后发生写入，再启用 Bleve 必须用新空目录全量重建。

### 本次生产验收

- 本机 Docker 构建 linux/amd64 镜像后传入生产，保留原数据库、加密配置和数据挂载。L2 一致性数据库导出经 gzip 校验约 25MB，不备份整份原文/附件目录；验收后同级自动备份只保留最近 2 次。
- 历史及期间新增合计 14,351 封已索引，pending/failed 均为 0，索引约 33MB。核心表数量与主键总和回查无异常；正常收到的新邮件被增量任务纳入索引。active 重启直接恢复可用，未重新回填。
- 以固定历史日期上界比较 7 组数据库/索引查询的总数及当前页 ID 顺序 SHA-256，全部一致，覆盖中文、数字、发件人、主题、正文、收/发件箱和第二页。影子检查未发现遗漏，但有限抽样不等于任意查询的全量一致性证明。
- 同一浏览器各连续 9 次完整列表请求，数字 `601`（566 条）p50 517ms / p95 613ms；正文 `项目`（2193 条）p50 202ms / p95 6859ms。切换后首个数字请求约 8.7 秒，后续第二页约 556ms。包含网络、COUNT 与数据库复核，不主动清缓存、无并发压测，不宣称所有搜索稳定低于 1 秒。
- 健康、现有登录态、列表、详情、附件 206 范围读取、账号、规则、文件夹、会话接口功能验证通过。无关键字会话列表首轮仍出现约 21 秒慢请求，尚未被本次搜索改造解决，需要独立优化。
- 并发冷读还出现过邮件/会话搜索 30 秒超时；随后温热并发复测分别约 548ms / 1895ms，无关键字邮件列表约 9696ms，均成功返回。因此生产性能尚不能承诺稳定秒级，需要继续定位冷读、并发和 SQL 执行计划，不能仅引用预热中位数宣称整页超时已彻底修复。

## 测试

2026-10-17 本机一次性 Docker MySQL 8（buffer pool 128MiB）合成测试：14,350 封，正文合计 90,414,758 字节（约 86.2MiB），601 查询得到 693 个候选。索引构建约 23.76 秒，当前磁盘占用约 25.9MiB；连续 9 次完整列表查询（包括 COUNT 和 SQL 复核），LIKE 中位 310.43ms、p95 362.16ms，Bleve 中位 19.31ms、p95 20.21ms。结果总数、顺序与数据库路径对照通过。此处为预热的合成样本，未清空系统缓存，没有模拟 NAS 磁盘和生产并发；不能拿本地 19ms 直接对比线上基线 16.65 秒，更不能宣称生产提升相同倍数。

构建耗时来自测试直接驱动小批，不包含默认后台 50ms 批间节流；正式后台回填时间还会受到节流、增量队列和 NAS 资源影响。

自动测试覆盖索引/数据库结果和顺序对照、中文单字、数字、邮箱、大小写、通配符、特殊 Unicode、字段组合、多用户隔离、未处理新增/更新覆盖、软删除、历史无任务回填、退避和精确确认、事务回滚、旧库补表、目录锁、重建互斥、重启续建、代际切换、损坏恢复、影子检查、并发搜索、关闭释放锁、鉴权和 envelope。合成性能不等于 NAS 真实邮件性能或生产 SLA。

代码入口：internal/searchindex/ 为引擎和生命周期，internal/storage/search_tasks.go 为持久化任务，internal/storage/search_provider.go 为查询适配，internal/api/search_handlers.go 为管理接口。
