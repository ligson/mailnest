# 生产部署与备份分级策略

本文档约定 Mail Nest 后续生产更新时的备份策略。目标是在“不丢用户数据”的前提下，避免每次普通代码更新都全量压缩几十 GB 的邮件数据目录。

## 核心原则

- 生产数据安全优先，但备份粒度要和变更风险匹配。
- 普通镜像升级不再默认全量打包 `data/`。
- 每次部署前都必须确认 `config.yaml`、数据库和 `data/` 仍是持久化挂载，不在一次性容器层中。
- 每次部署都要记录当前镜像标签、回滚标签、备份内容和验证结果。
- 每次自动备份必须放到独立目录，不能把所有 `.tgz`、SQL、记录文件平铺在同一个目录里。
- 自动备份默认只保留最近 2 次，部署验证通过后清理更早的同级自动备份，避免长期浪费 NAS 空间。
- 任何备份文件、数据库导出、真实配置和 NAS 连接信息都不得提交到仓库。

## 备份目录与保留策略

建议生产备份目录按风险级别拆分：

```text
backups/
  deploy-light/
    20260730112000-ui-fix/
      docker-compose.yml
      config.yaml
      image-tags.txt
      rollback.txt
  database/
    20260730113000-schema-change/
      docker-compose.yml
      config.yaml
      image-tags.txt
      mailnest.sql.gz
      rollback.txt
  data-risk/
    20260730114000-attachment-path/
      docker-compose.yml
      config.yaml
      image-tags.txt
      affected-data.tgz
      rollback.txt
  manual-keep/
    20260730115000-sqlite-to-mysql/
      README.txt
```

保留规则：

- `deploy-light/`、`database/`、`data-risk/` 下的自动备份，每类默认只保留最近 2 个目录。
- 新备份完成且本次部署验证通过后，再删除同类更早的自动备份。
- `manual-keep/` 只放明确需要长期保留的迁移或事故备份，不参与自动清理；放入前必须写清楚原因和预计清理时间。
- 清理备份时只删除 `backups/` 下符合命名规则的历史备份目录，不递归删除生产 `data/`、`config.yaml`、`docker-compose.yml` 或数据库目录。
- 如果本次部署失败或还没验证通过，不清理旧备份。

## 备份分级

### L0：无需生产数据备份

适用场景：

- 只修改文档、README、CHANGELOG。
- 只提交代码但不部署生产。

要求：

- 不需要备份生产数据。
- 仍需要检查本地工作区，避免提交敏感信息。

### L1：轻量部署备份

适用场景：

- 只更新前端静态资源。
- 只更新后端普通业务逻辑，且不修改数据库 schema、不修改邮件原文/正文/附件存储路径。
- 只调整 UI、接口展示、查询条件、样式、日志文案。

备份内容：

- 远端 `docker-compose.yml`。
- 远端真实 `config.yaml`。
- 当前正在运行的前后端镜像标签记录。
- 回滚说明 `rollback.txt`。

不做：

- 不全量压缩 `data/`。
- 不导出完整附件和邮件原文目录。

回滚方式：

- 恢复旧 `docker-compose.yml` 或旧镜像标签。
- 执行 `docker compose up -d`。

### L2：数据库变更备份

适用场景：

- 新增或修改数据库表、字段、索引。
- 修改 GORM model 或显式迁移逻辑。
- 修改登录、用户、邮箱账号、规则、联系人等数据库核心数据结构。

备份内容：

- L1 的全部内容。
- 数据库备份：MySQL 使用逻辑 dump；SQLite 先停止后端或确保一致性后复制数据库文件。
- 备份目录放到 `backups/database/{时间戳}-{说明}/`，部署验证通过后只保留最近 2 个自动数据库备份目录。

不做：

- 如果本次不修改 `raw.eml`、正文文件、附件路径或数据目录结构，不全量压缩 `data/`。

回滚方式：

- 先回滚镜像标签。
- 如数据库迁移不可逆或迁移后数据异常，再按备份恢复数据库。

### L3：文件数据高风险备份

适用场景：

- 修改邮件原文、正文、附件、头像、导入临时文件的存储路径或读写格式。
- 批量移动、删除、清理或重写 `data/` 下的文件。
- 修改 EML 导入落盘逻辑、附件落盘逻辑，并可能影响既有文件读取。
- 执行生产数据清理、迁移、批量修复。

优先备份方式：

- 优先使用 NAS 快照、Btrfs 快照、Hyper Backup、restic、borg 或 rsync 增量备份。
- 如果没有可用的快照或增量备份，再考虑压缩相关子目录。
- 只有在涉及整个 `data/` 目录结构或无法精确界定影响范围时，才全量压缩 `data/`。
- 自动文件数据备份放到 `backups/data-risk/{时间戳}-{说明}/`，部署验证通过后默认只保留最近 2 个自动备份目录。

回滚方式：

- 优先恢复受影响子目录或文件。
- 需要时回滚数据库和镜像标签。

### L4：不可逆或大规模迁移

适用场景：

- SQLite 到 MySQL、MySQL 到 PostgreSQL 等数据库迁移。
- 数据目录整体迁移到新磁盘、新路径或新挂载方式。
- 大规模历史数据重建，且失败后无法通过重新运行恢复。

要求：

- 必须先写清楚迁移步骤、验证步骤和回滚步骤。
- 必须同时备份配置、数据库和受影响的数据目录。
- 优先使用快照或增量备份；全量压缩只作为没有快照能力时的兜底。
- 没有备份和回滚方案时不得执行。

## 默认执行建议

- 前端/UI 更新：使用 L1。
- 后端普通功能更新：默认 L1；如果包含数据库迁移则升为 L2。
- 数据库 schema 更新：使用 L2。
- EML 导入、附件、邮件正文显示逻辑更新：如果只改解析或展示且不重写旧文件，使用 L1 或 L2；如果会改写旧文件，使用 L3。
- 批量删除或清理生产数据：使用 L3，且必须先做精确查询和可回滚备份。
- 数据库或数据目录迁移：使用 L4。

## 部署后验证

每次生产部署后至少验证：

- `/api/v1/health` 健康检查。
- `/mail` 前端页面可访问。
- 当前容器镜像标签符合预期。
- 登录、邮件列表和邮件详情仍可用。

涉及对应能力时额外验证：

- 数据库变更：检查迁移日志、核心表字段、登录和列表查询。
- 邮件文件变更：检查邮件正文、内嵌图片、附件下载或预览。
- EML 导入变更：检查上传会话、续传、去重和失败提示。
- 规则或文件夹变更：检查规则列表、规则执行和文件夹归属。
